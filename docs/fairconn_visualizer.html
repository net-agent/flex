DRR · quantum · writev

FairConn 写路径：从 per-stream 队列到 writev

FairConn 只替换 packet.Conn 的写路径：包先进入所属 SID 的队列，SID 被激活后进入 readyQueue；调度循环优先排空控制通道，再按轮转取一个 SID，一次发送 quantum 个包。读路径不受影响。

quantum 2 controlCh 128 readyQueue 1024 writev batch
步骤 1 / 6

quantum · 每次访问的包预算

默认 2。16KB 包时一次 visit 最多 32KB；64B 包时只有 128B。它同时决定公平粒度与单流连续占用链路的时间。

controlCh · 跨流控制包

Open / ACK / Ping / CloseAck 走独立高优先级通道（容量 128）。drainControl() 一次排空，保证 ACK 不被数据突发饿死，但也意味着大量控制包可以反过来压制数据。

readyQueue · 就绪 SID 轮转

容量 1024，FIFO。SID 通过 active CAS 保证最多出现一次；队列满时 requeue 会退化为异步 goroutine——几千条活跃流时需要关注。

writev · 批量写与缓冲回收

processStream 用 Drain(quantum) 取一批包，WriteBufferBatch 走 net.Buffers 一次写出；写完后统一 PutBuffer。switcher 转发路径用 WriteBufferOwned 避免 cloneBuffer 拷贝。

为什么需要 FairConn？ 没有它时，一条持续写 16KB 包的流会长期占住 packet.Conn 的写锁，ACK、Ping、OpenStream 只能排在它后面；接收端窗口无法及时补充，表现为"大流量把控制面饿死"。FairConn 用 per-SID 队列 + 轮转把"一次能连续写多少"从"应用写多少"变成"quantum 个包"，控制包则走更高优先级的通道。

三种公平单位，没有绝对优劣

C / A / B 的差别不在"谁更公平"，而在用什么单位衡量公平：包、payload 字节、还是（近似的）线缆成本。选型取决于你要保护的是交互延迟、带宽份额，还是链路不被小包洪水吞掉。

C · 包数 quantum

每次 visit ≤ quantum 个包 公平单位 = packet

当前 FairConn 的实现。每个就绪流每轮最多发 quantum 个包，然后让出。

  • 保护：交互延迟、实现简单、无额外状态
  • 偏向：大包流的 payload 字节份额
  • 参数：quantum（默认 2）
  • 适合：通用网关、内网、延迟优先

A · 字节 DRR

deficit += Q while deficit ≥ len(p): send; deficit -= len(p) 公平单位 = payload byte

每个流按字节预算轮转，deficit 跨轮携带，理论上让每条流拿到相同的 payload 字节。

  • 保护：带宽份额（大包/小包一视同仁）
  • 代价：小包流的 52B/1B 线缆放大；大 Q 带来队头延迟
  • 参数：Q（字节）、包数上限
  • 适合：包长接近、可接受监控成本的场景

B · 成本计费

charge = max(len(p), minCharge) while budget ≥ charge: send; budget -= charge 公平单位 = 近似线缆成本

按"车道占用"计费：小包有最低计费，预算除以便得到每次 visit 的包数上限。

  • 保护：链路不被 1B 包洪水吞掉；延迟可控
  • 代价：小包 payload 份额被压低
  • 参数：Q、minCharge（包数 ≤ Q/minCharge）
  • 适合：公网/多租户中继、混合包长

假设每个 flex 包独立成帧、无 Nagle 合并。writev 减少了系统调用，但不会消除每个包的头。A 方案若按 payload 字节给 1B 流公平份额，它需要 32K 个包才能拿到 32KB payload——线缆上约 1.7MB。

关键结论：A 的"公平"在包长差异大时并不免费。要么接受线缆放大，要么加包数上限（公平性退化），要么按线缆成本计费（就是 B）。

选型建议

从"你要保护什么"倒推，而不是从"哪个名字更公平"倒推

recommendation

默认：C · quantum=2

交互延迟优先、改动最小。当前实现就是它；实测 quantum 2→4 约 3–8% 吞吐提升，但单次占用翻倍。若流量以大包为主，可用 4。

多租户：B · Q=32KB / min=1KB

按成本分配，天然限制 1B 包洪水；每次最多 32 个包。代价是小包流 payload 份额低——交互流通常不需要大带宽，换取的是低延迟与链路稳定。

A：只在包长接近时使用

如果所有流都是 16KB 或都是 1KB，A 很干净。混合包长时建议设包数上限并监控线缆放大；否则 1B 流会把"公平份额"变成链路攻击面。

独立项：控制通道排空上限

drainControl() 当前一次排空。ACK 洪水可以反过来压制数据；可加"每轮最多 64 个控制包"的上限，与 A/B/C 的选择无关。

如果实现 A / B，需要处理这些边界

按优先级排序

implementation notes
  1. Close 帧不能被预算饿死：CloseStream / AckCloseStream 是 0 payload，仍与数据共享 per-stream 队列；必须强制放行，或把它们提升到控制通道。
  2. 单包大于 Q 要允许 overshoot：64KB 包遇到 32KB 预算时不能永远等待；发送一个包、deficit 记负，再让出。
  3. deficit 要有上界：包数上限截断 visit 时，未花完的 deficit 若无限累积会形成"信用炸弹"；建议钳制在 Q 附近。
  4. 优先用 minCharge 而不是独立 packet cap：包数上限会直接破坏字节公平；minCharge 同时限制包数与线缆成本。
  5. 测试要混合包长：现有公平性测试各流 payload 相同，测不出 16KB vs 64B 的偏差；至少覆盖 16KB / 1KB / 64B / 1B 四类，并同时断言 payload 份额、wire 放大与 p99 间隔。
  6. 参数要可配：目前 Server/Session 只暴露 SetEnableFairConn；应增加 SchedulerConfig{QuantumPackets | QuantumBytes, MinChargeBytes}。
建议的落地顺序：先把现有 quantum 做成可配（默认 2，行为不变），再以配置项引入 B（默认关闭），用混合包长基准对比 C2 / C4 / B 的吞吐、p99 间隔与 wire 放大，最后再决定是否把 B 设为默认。
页面上的对比表已经把四种策略放在同一 workload 下；把它与 go test -bench 的实测吞吐结合看，避免只凭公平性指标做决定。

模型边界

这是教学模型，不是基准测试

scope
